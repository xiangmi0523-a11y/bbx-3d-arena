# E5 前置核查：authority 下限在针尖对针尖僵持中不作用于物理（实验暂停）

- 分支：`feat/low-speed-stall-e5`，基线 Stage A `2f573ab`。`src/` 没有改动，只新增 `tests/diag/e5authority.diag.ts`。
- 标注：**[实测]** 表示固定种子运行直接得到；**[代码]** 表示读源码得出。

## 结论

按任务要求，"必须先完成的代码核查"没有通过，**实验暂停，没有改用其他控制变量**。

原因：在针尖对针尖确认僵持期间，把 authority 抬到 0.3 或 0.6，物理上没有任何作用。

- **[代码]** BeyPhysics 只在牵引门打开时才读取 authority。
- **[实测]** 针尖对针尖僵持时，牵引门一直是关的。
- **[实测]** B、C 两组与 A 组在 24 场针尖对针尖中逐步状态 hash 完全相同（48/48）。

## 1. authority 的定义与调用链 [代码]

**计算位置：** `MotionIntent.update`（src/game/beys/motionIntent.ts:463）

```
authority = min(0.9, a × tipAuthority × spinK)
```

各项含义：

| 项 | 来源 / 取值 |
|---|---|
| `a` | 战术状态决定的调制深度：cut、orbit、contact、guard、evade 各有取值，roam / launch 为 0；墙边保护取 `edgeA × 深入程度`；最后乘以 min(1, 速度误差 / errFull) |
| `tipAuthority` | 0.3 + 0.7 × clamp(drift / 0.16)；针尖 drift 0.03，所以约为 0.43 |
| `spinK` | 由转速比例决定：转速比例在 0.1 以下为 0，到 0.35 时为 1 |

**唯一读取位置：** `BeyPhysics.preStep`

- 第 482 行：`steering = this.breakout > 0 ? 0 : this.intent.authority`。这一句位于第 449 行的条件块内：

```
if (driveGrip >= driveMinGrip && grounded && !dashing && spin > 2·minStableSpin)
```

  其中针尖的 `driveGrip` = gearGrip 0.1。只有两种情况会把它抬高：脱困（取 breakoutGrip 0.35，但脱困时 steering 被强制为 0），以及墙边（按 edgeGrip × edgeW）。
- 在条件块外，`steering` 保持初值 0。

**steering 作用的物理变量：进动相位的角速度。**

- 第 524–531 行：`rate = 自然进动角速度 × (1 − steering × cos Δ)`，其中 Δ 是"牵引方向与 heading 的夹角"。
- 进动相位决定自稳控制的目标倾斜方向（第 548–556 行）。BeyPhysics 用 `setAngvel` 修改垂直于转轴的角速度分量，让实际转轴转向这个目标。

**它为什么不会直接变成水平推力：**

- 这条链上没有任何 `applyImpulse` 调用，也不修改线速度。
- steering 改的只是转轴的倾斜方向。水平运动只能间接产生：接触点相对转轴的偏移变了，Rapier 针尖–地面摩擦的方向随之改变。E1 测得，停滞时唯一的正功率来源正是这种摩擦。
- 另外，`setAngvel` 写入的垂直角速度本身也会让接触点滑移（E1 中滑移的"垂直角速度项"P50 为 0.032 m/s），这同样经由 Rapier 摩擦起作用。
- 结论：只要 steering 能到达进动，它影响的是摩擦方向而不是推力。但在现有代码中，针尖在中心僵持时它根本到达不了进动。

## 2. 实测 [实测]

诊断覆盖的做法：只包装 `intent.update`，在确认僵持时把 authority 取 max(原值, 下限)。

**确认僵持**（全部满足）：
- 双方都是针尖
- 双方速度 < 0.4 m/s
- 接触结束 > 6 步
- 双方转速比例 ≥ 0.4
- wobble 计时为 0，双方不在脱困
- 以上持续 ≥ 3 s

**结果：**

- **每场确认僵持的步数：** 3801–6412 步。B、C 组每场被抬高 authority 的 台·步 为 7602–12824。
- **确认僵持期间牵引门打开的步数：** 每场、每组都是 **0**。
- **24 场针尖对针尖的 hash：** B 对 A 24/24 相同，C 对 A 24/24 相同。
- **156 场非针尖对针尖：** B、C 对 A 都是 312/312 相同。这些场次本来就不满足"确认僵持"条件，所以相同是预期中的。
- **A 组对 Stage A 基线（cb4c2c4 plain-B）：** 180/180 一致（`verify-A-vs-stageA.json`）。
- **整场对局中 authority > 0 且确实到达物理的步数：** 只出现在 4 场（LONG S/S#1 18 步、NNPOW 0.9#2 93 步、CTRL wall NN#0 52 步、CTRL wall NN#1 45 步），而且都在墙边保护打开牵引门时，不在僵持状态里。

## 3. 当前僵持分类与 R1c 的差异 [代码]

- 本核查的"确认僵持"与 R1c 的 dwell 一样，都持续 3 s，转速比例阈值都是 0.4。
- 不同之处：本核查不要求"间隙 ≤ 0.25 m"，不检查转速不平衡，也不检查 R1c 的 `traction` 条件。在这里牵引门本来就关着，这一点已由实测确认。
- 两者都不会在 wobble 期间生效。

## 4. Wobble 的优先级 [代码]

- `BattleSystem.watchStall` → `isDeathWobble`：低转速一方的转速比例 < 0.25，倾斜超过自然倾角 0.25 rad，持续贴靠 0.8 s，且对方健康。
- 触发后，较健康的一方进入脱困（breakout）。脱困期间 steering 被强制为 0。
- Wobble 只在转速比例 < 0.25 时触发，落在本实验"转速比例 ≥ 0.4"的范围之外。确认僵持条件里也要求 wobble 计时为 0、双方不在脱困。
