## 3. 要求 2：随机种子与可信测试基线（阶段 1 第一项）

### 3.1 全局随机源清单（B0 / 2f573ab）【事实：`git grep`】

| 位置 | 用途 | 影响物理/战斗？ | 现状 |
|---|---|---|---|
| `beys/BeyPhysics.ts:168` | 进动初相 `Math.random()*2π` | **是** | 构造时字段初始化 |
| `beys/BeyPhysics.ts:183` | 战术意图种子（`launch.seed` 缺省时） | **是** | 游戏内永远缺省 |
| `launcher/launch.ts:57` `rivalCommand` | 对手力度与方向 | **是** | 默认参数 `Math.random` |
| `render/ImpactFX.ts`（约 25 处） | 火花方向、寿命、闪烁 | 否（视觉） | 与物理共用全局 `Math.random` |
| `audio/AudioFX.ts`（6 处） | 噪声缓冲、起始偏移、音高抖动 | 否 | 同上 |
| `garage/GarageView.ts:157` | 组装界面动画角度 | 否 | 同上 |
| `performance.now`（GameEngine、手势） | 帧时间、手势速度→发射力度 | **间接是**（玩家发射参数、每帧物理步数） | 非随机但非确定 |

**关键耦合**【推断，有代码证据】：视觉/音频与物理共用同一个全局 `Math.random`。测试里用 `Math.random = seeded(n)` 固定种子时，只要某次运行多消耗或少消耗一个随机数（例如 ImpactFX 被实例化、或测试执行顺序变化），物理用到的随机数就会整体错位。

### 3.3 非确定性来源分类

| 来源 | 类型 | 处理 |
|---|---|---|
| 进动初相、意图种子、对手发射 | 可控随机 | 由每局种子派生（3.4） |
| 视觉/音频随机 | 可控随机，但不应影响物理 | 独立的“表现随机源”，不与物理共享 |
| 玩家手势时间 | 输入 | 测试中以 `LaunchCommand` 直接给定；录像回放记录命令 |
| 渲染帧间隔 → 每帧物理步数 | 时序 | 物理是固定 120 Hz 步长，步数只决定“何时”算，不改变每步结果【推断】；回放以步为单位 |
| Rapier 浮点与 WASM 平台差异 | 平台 | 同平台同构建确定【推断】；跨平台差异已观察到（macOS arm64 贴墙频率 1.28 vs 阈值 1.2）【报告】。**存在同版本的 `@dimforge/rapier3d-deterministic-compat@0.19.3`**【事实：npm registry】，可作为跨平台确定性候选【待实验：性能代价，尤其 iPhone】 |
| 测试执行顺序 / 并行 | 时序 | 种子不再依赖全局状态后自然消除 |

### 3.4 种子注入与传播设计

- 新增 `MatchRandom`：一局一个 `matchSeed`，按用途派生互相独立的子流：`precession[side]`、`intent[side]`、`rivalLaunch`、`fx`、`audio`。派生用固定哈希（如 `mulberry32(hash(matchSeed, tag))`），任何子流多用或少用都不影响其他子流。
- 物理与战斗只从 BattleSystem 拿随机源；表现层拿 `fx/audio` 子流；GarageView 可继续用表现随机。
- 游戏里 `matchSeed` 每局生成一次并记录在结果和诊断数据里，便于真机问题复现。
- 发射参数、场景、对手组合、初始倾角都进入“场景描述”（JSON），与 `matchSeed` 一起构成可复现的最小单位。

### 3.5 测试集划分

| 类别 | 定义 | 标准 | 示例 |
|---|---|---|---|
| 确定性回归 | 相同场景描述 + 相同种子 → 逐步相同 | 逐步哈希或关键量完全相等；任何变化都需要在提交说明里解释 | 穿地、恢复系数 < 1、一次碰撞只结算一次、惯量契约 |
| 多种子统计 | 固定的种子集合（如 32 或 64 个），评价分布 | 用分位数/比例 + 置信区间作断言；种子集合本身固定，所以结果仍然可复现 | 三种类型差异、撞墙频率、节奏、僵持矩阵 |
| 记录的非确定性 | 已知且接受的非确定来源 | 不进断言，只记录 | 跨平台浮点（直到确定性构建评估完成） |

“三种类型差异”的处理：拆成两部分——惯量排序（确定性，单测）+ 类型行为差异（多种子统计：例如 32 个种子中“耐力型平均存活时间更长”的比例 ≥ 某阈值，阈值由阶段 1 首次在 B1 上测出的分布确定后写入，之后作为回归基准）。**不允许用重试次数掩盖随机性。**

### 3.6 失败自动记录与复现

- 统计测试失败时，把失败种子、场景描述、关键时间序列写入 `test-results/`（CI artifact），并打印一条可直接运行的复现命令。
- 已有的录像/回放工具（60d1ec0 的 `tools/replay`）接受同一份场景描述 + 种子即可重放。

### 3.7 阶段 1 种子工作的完成条件

- `src/` 中影响物理/战斗的 `Math.random` 调用为 0；表现层随机与物理随机分离。
- 全量测试在同一机器上连续 3 次结果完全一致。

## 5. 要求 4：完整惯量契约

### 5.1 B0 上的只读测量（64 种 Blade×Disc×Tip 组合）【事实】

方法：在 2f573ab 上按游戏代码创建 `BeyPhysics` 刚体（不推进模拟），读取 `body.mass()`、`localCom()`、`principalInertia()`、`principalInertiaLocalFrame()`，与 `assembleBey` 的 spec 比较。

| 项目 | 结果 |
|---|---|
| 总质量 | 64/64 与 spec.totalMass 完全一致 |
| 质心 | 全部位于转轴上（水平偏移 0）；高度与按层估算值最大差 0.001 |
| 碰撞体形状 | 球 + 3 个圆柱，全部绕自转轴对称 |
| 惯量张量 | Ix = Iz（64/64），主轴坐标系为单位旋转（无倾斜主轴） |
| 自转轴惯量 Iy / spec.spinInertia | **0.64 – 1.01**；泰坦王冠系列约 0.64–0.67，平衡/防御约 0.85–0.92，攻击约 1.0 |
| 横向惯量 Ix | 只存在于 Rapier（约 0.28–0.33）；spec 中**没有横向惯量的定义** |

结论：
- 问题不只是“一个标量不相等”。spec 只有自转轴标量，而 Rapier 的完整张量来自形状 + 质量；rimWeight 只影响脚本那一半【事实】。
- 物理碰撞体完全轴对称，所以**非对称结构（刀刃凸起、偏心配重）目前在物理中根本不存在**，测得的张量非对角项为 0【事实】。这是现状测量，不是契约豁免：裁决 §5 要求非对称结构考虑完整张量，所以契约从一开始就按完整 3×3 张量建模、存储和测试（5.2、5.3），今后加入非对称碰撞体或偏心配重时不需要改契约结构。
- 本次测量未覆盖“各零件单独的质量分布”：spec 只给整台质量与自转轴惯量，零件级分布要在阶段 1 建契约时补数据【未知】。

### 5.2 契约定义（阶段 1 实施）

1. **单一来源**：每个零件给出质量、质心（本地）、本地完整 3×3 惯量张量（含 rimWeight 的分布模型，非对角项显式给出，轴对称件为 0）；`assembleBey` 用平行轴定理组合出整台的质量、质心、完整张量，再对角化得到主惯量与主轴。
2. **写入 Rapier**：通过碰撞体 `setMassProperties`（质量、质心、主惯量、主轴旋转）或刚体附加质量属性写入；碰撞形状只负责接触，不再隐式决定惯量。具体走哪条 API、与碰撞体密度如何互斥，需在实施时按 Rapier 0.19.3 文档与读回结果确认【待实验】。
3. **读回校验**：创建后读回 Rapier 的质量、质心、主惯量、主轴，与 spec 比较。
4. **游戏层使用同一数据**：转速衰减、撞击掉速、能量账本都用这份张量。
5. **坐标系**：本地原点仍在轴心最底部，Y 为自转轴；文档写明 spec→Rapier 的转换（Rapier 质量属性以碰撞体/刚体本地坐标表达）。

### 5.3 契约测试

- 64 种组合：质量误差 < 0.1%；质心误差 < 1 mm（游戏单位 0.001）；Ix/Iy/Iz 误差 < 2%；主轴偏差 < 0.5°；由读回主惯量与主轴重建的完整张量与 spec 张量逐元素相对误差 < 2%（含非对角项）。

- 预期行为变化：耐力型碰撞掉速降低（应该如此）；这是阶段 1 中唯一刻意改变物理结果的提交，单独回滚。

## 6. 要求 5：能量与角动量账本

### 6.1 记录内容（每台陀螺、每步）

| 项 | 计算 |
|---|---|
| 平动动能 | ½ m v² |
| 转动动能 | ½ ωᵀ I ω（世界系，用完整张量） |
| 重力势能 | m g h（质心高度） |
| 角动量 | L = I ω（世界系）、绕质心与绕原点各一份 |
| 游戏层写入引起的变化 | `preStep` 读到的 ω_read 与 `setAngvel` 写入的 ω_write 之间的动能差与角动量差，按来源拆分：转速衰减、自稳 PD、进动对齐、`loseSpin`、`wobble` |
| 游戏层冲量做功 | 牵引、轨道冲刺、滚阻、刀刃咬合冲量（`applyImpulse*`）各自的功 |
| Rapier 求解引起的变化 | 步前（写入后）与步后（求解后）之差，按接触对汇总；可用流形冲量 × 接触点速度估算摩擦与碰撞耗散 |
| 碰撞前后 | 以 ContactFacts 的接触段为单位记录两台的总能量与角动量变化 |
| 残差 | 总变化 − 上述各项之和；记录数值误差量级 |

口径：角速度变化不等于能量损失。所有能量项用质量、完整惯量张量、线速度和角速度一起计算；只看 `spin` 下降不能判断能量去向【裁决 §6】。

### 6.2 重点调查：`setAngvel` 与约束求解的交互

- 现状【事实】：`BeyPhysics.preStep` 每步读出 ω、修改自转大小和横向分量（PD 自稳）、再 `setAngvel` 写回；Rapier 随后求解接触。Muse 报告的残余为 9.0→49.1 W（占损失 16%→52%）【报告，未复核】。

## 7. 要求 6：阶段 2 运动控制接口与 A/B 对照

### 7.1 闭环结构【裁决】

战术层（Tactical AI）→ 运动控制接口（Motion Controller）→ 轴心驱动模型 → Rapier 物理 → 统一观测（ContactFacts + 运动状态 + 账本）→ 回到战术层。

### 7.2 控制接口

| 字段 | 含义 |
|---|---|
| `direction` | 期望的水平运动方向（世界系单位向量） |
| `intensity` | 0–1，控制强度（意愿，不是力） |
| `target` | 可选：目标点或目标对手的预测点 |
| `validUntil` | 有效期限（步数或秒），过期视为无指令 |
| `priority/mode` | 可选：切入、环绕、守中、脱离等，仅供执行器选择策略 |

执行器返回（每步反馈给战术层）：实际可用的最大加速度、实际施加的加速度方向与大小、本步自转消耗、指令是否被物理限制截断、指令有效度（实际加速度在期望方向上的投影 / 可用上限）。

更新频率：战术层低频（初始 30 Hz）【待实验】；执行器每物理步（120 Hz）。

物理限制（硬约束）：执行器只能通过轴心–地面接触产生力，力的上限由接触半径、摩擦、法向力、倾斜状态、剩余转速决定；不得瞬移、直接设置速度、强制朝向；每份力都按账本扣自转。**任何轴心都不能因为低于门槛被完全关闭控制**：能力可以很小，但必须连续【裁决】。

### 7.3 两个候选执行器【裁决：都保留为候选】

- **A 方向 + 强度执行器**：按指令方向在物理上限内产生驱动力。
- **B 相位偏置执行器**：保留现有“调节进动相位转速”的方式，接到同一接口（`direction`→期望方向，`intensity`→调制深度）。为满足“不能完全关闭控制”，B 也必须改为连续的驱动能力（不再由 `gearGrip ≥ 0.2` 门控）。
- Claude 的论点：B 在针尖/低速时执行能力为 0，且牵引方向每约 1.8 s 转一圈、矢量和接近 0（第一轮审查推导）。Muse 的论点：B 治好了第一轮的机械感，开环本身不是错误，应先闭环、加记忆。**两种论点都保留，由实验决定。**

### 7.4 公平对照协议

- 同一套场景描述 + 种子集合（第 3 节）；同一组合矩阵（4 轴心 × 4 Blade，对手固定为若干代表组合）；同一场地；同一时长；同一战术层（只换执行器）；同一账本口径。
- 指标：实际加速度与期望方向夹角分布；有效位移（净位移/路径）；控制响应延迟（指令变化→加速度方向变化的步数）；单位有效位移的自转消耗；路径曲率连续性；追击成功率、切入有效率（第 8 节定义）；碰撞后恢复（分离后重新接近的时间与比例）。
- 判定：不得只看单一场景或单一指标；需要在各轴心类别上分别报告，并附真机观感（第 8 节）。按实际运动结果、物理约束、能量消耗和战斗体验四方面决定，不凭理论偏好提前定胜负【裁决 §3.1】；初始状态、种子、陀螺/部件、场地、对手、统计口径六项必须相同。

| 自转消耗–运动收益 | 单位有效位移的自转消耗，按轴心与状态分别统计 |
| 条件覆盖 | 发射方向（aim −1…1）、初始转速（力度 0.3…1）、倾角、场地位置（中心/中段/墙边）组合；多种轴心 × Blade 组合；**不同对手行为**（追击型、守中型、无指令/被动），不能只用少数固定场景【裁决 §7】 |
| **核心场景** | 球头对球头（疾风新月/潮汐堡垒 + 圆顶球轴）与针尖对针尖：双方低速贴近不超过阈值，且不使用任何程序性拉开【裁决】 |

“加速度方向发生变化”不能替代“追击成立”【裁决】。真机：产品负责人对上述核心场景与默认组合各 10 局给出主观评价。

## 9. 要求 8：阶段 5 真机性能验收

### 9.1 原则【裁决】

不裁定 GPU 受限，也不裁定 48 fps 必然是 48 Hz 档位。不以“所有设备稳定 60 fps”为无条件硬标准；以设备实际可用的刷新档位为基准，考核帧节奏稳定性、漏帧、性能余量与画质档位效果。

### 9.2 六类数据与测量方案

| 数据 | 方案 | 依赖 / 限制 |
|---|---|---|
| 原生显示刷新节奏 | Capacitor 原生插件：`CADisplayLink` 记录 `timestamp/targetTimestamp`，读取 `UIScreen.maximumFramesPerSecond`、`preferredFrameRateRange`，与 JS 侧时间对齐导出 | 需要写 Swift 插件（阶段 5 实施）；ProMotion 下 WKWebView 是否允许 120 Hz【假设，需测】 |
| WebView rAF 节奏 | 移植 stage0 诊断面板（PerfRecorder），记录 rAF 间隔分布 | 9d70f19 手工移植，GameEngine 一处冲突【事实】 |
| CPU 主线程耗时 | 现有分段计时（physics/sync/fx/cam/ui/renderSubmit）+ 诊断面板 | 已有 |
| GPU 工作时间 | ① Xcode Instruments（Metal System Trace / GPU Counters）连机分析；② WebGL 计时扩展在 iOS WebKit 上不可用【推断】，所以浏览器内无法直接测 | **Instruments 需要 Mac + Xcode + 可调试签名（get-task-allow）**；当前流程是未签名 IPA + 自签安装【事实：项目记忆】。用户是否有 Mac【未知】 |
| 帧间隔分布 | 诊断面板：P50/P95/P99、长帧、相对实际刷新档位的漏帧率（PR #8 节奏识别） | 已有 |
| 持续运行降频/降档 | 原生插件读 `ProcessInfo.thermalState` 与低电量模式；JS 侧记录画质档位变化时刻；10 分钟连续对战 | 需原生插件 |

### 9.3 判读规则

- 帧间隔稳定在某档位（如 20.8 ms）≠ 没有 GPU 压力：必须同时看原生刷新档位、CPU 余量与 GPU 时间【裁决】。
- rAF 约 48 Hz ≠ GPU 瓶颈：需要原生刷新档位为 60/120 Hz 且出现漏帧，才算掉帧。

### 9.4 画质 A/B

同一设备、同一组合、同一种子、锁定档位，各跑 60 s ×3 次（冷机/热机分开）；比较漏帧率、P95/P99、CPU 分段、温度状态、档位切换次数。B1 与 e72164c 包对照只比画质。

### 9.5 验收（阶段 5 完成条件）

在目标设备的实际刷新档位下：锁定默认档 60 s 漏帧率低于阈值、P99 不超过 2 个刷新周期；10 分钟内不出现非温度原因的降档；有温度降档时记录并给出档位策略。阈值在阶段 5 开工时按首轮真机数据确定。
