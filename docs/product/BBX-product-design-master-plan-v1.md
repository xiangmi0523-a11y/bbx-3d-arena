## 0. 结论摘要

**现状一句话【事实】**：仓库已有一条能玩的单局链路（标题 → 组装 → 拉绳发射 → 自主对战 → 单局结果），4×4×4 部件可换、物理与视觉分离做得好、撞击反馈与画质分档成熟；但它还不是"游戏"：没有赛制、没有模式、没有对手列表、没有进度，四类陀螺的差异在碰撞里几乎只靠几个对称的标量，爆裂没有实现，场地只有一张且发射位置左右不对称。

**我对任务书初步构想的主要修改（独立判断）**：

1. **把"一局"从一次发射改成"回合制积分赛"**（先到 4 分，回合间可换一个零件、双方换边）。理由：发射后是自主对战，玩家唯一能施加影响的地方就是赛前和回合之间。单次 15 秒的物理模拟决策太少；多回合 + 赛间调整把玩家决策次数从 1 次提高到 4–7 次，同时把单场时长拉到 2–4 分钟这一手机对战的合适区间。这是本方案最核心的改动。
2. **四类陀螺用"赢的方式"区分，而不是用属性条区分**：攻击型靠出界 / 极限终结得高分但有自毁风险；防守型靠承受与反弹让对手自己出界；耐力型靠旋转终结；平衡型用"随转速切换行为"的轴心实现前后半场性格不同（不是平均数值）。克制是软克制（目标胜率 55–65%），不是硬克制。
3. **展示属性改为"实测属性"**：属性条不再用手写公式（现在的 `computeStats` 注释写着"只给 UI 用，不参与物理"），而是用已经建好的确定性无头模拟，对每个组合跑标准测试，把测量结果写成数据表给 UI。这样"属性条说的"就等于"实际打出来的"。
4. **零件名称沿用仓库已有的 Blade / Disc / Tip 体系（中文：刃环 / 锁盘 / 轴心）**，不改用任务书里的 Ratchet / Bit 和"3-60"式编号；HUD 里现有的 "XTREME DASH" 字样建议改为原创名称。理由见第 11 节。
5. **地图少而精**：首发只做 1 张标准场（修正发射对称性、把"极限轨道"从脚本冲刺变成有几何与材质的真实区域、口袋改用传感器判定），第 2 张在 MVP 之后。任务书概念图里 6 张"换皮"地图不进首发。
6. **本地同屏双人提前**：因为发射后是自主对战，本地双人只需要两套发射输入，不需要实时操作同步，成本很低，放进 MVP 之后的第一个扩展版本。在线对战不承诺。
7. **路线分两条并行轨道**：A 轨是 ChatGPT 裁决里的物理 / 运动 / 碰撞阶段（1→4），B 轨是不依赖驱动模型的"产品外壳"（赛制、模式、存档、页面、内容数据层、画质低档）。B 轨可以马上开工，不被球头 / 针尖僵持阻塞；两条轨道在"四型可辨"里程碑汇合。

**真正需要用户决定的只有 5 件事**（第 14.3 节）：产品名称与商标风险、回合制积分赛是否作为标准对局、是否加入爆裂终结、首发内容规模、玩家赛前"战术指令"是否保留。

## 3. 产品结构：核心循环与信息架构

### 3.1 三层循环【设计】

```
秒级（单回合 10–40 秒）
  发射决策（力度 / 方向 / 倾角 / 发射位）→ 自主对战观看 → 终结 → 得分
        │
分钟级（一场比赛 2–4 分钟）
  选对手情报 → 选构筑 → 回合 1 → 赛间调整（换 1 个零件 / 换战术）→ 回合 2 … → 先到 4 分获胜
        │
天级（长期）
  挑战之路推进 → 解锁零件 / 对手 / 场地 → 组装新构筑 → 在更难的对手或赛制中验证
```

**为什么这样设计**：
- 方向已定"发射后自主"【任务书 2】，所以玩家的"操作"只能放在发射与赛前。单回合决策太少，必须靠回合制把决策次数堆起来，并让"上一回合看到了什么 → 下一回合怎么改"成为核心乐趣（观察 → 推理 → 调整）。
- 回合间换零件把"组装系统"从菜单功能变成比赛中的战术工具，直接回答任务书验收第 5 条"组装系统是否真正影响战斗"。
- 积分差异（spin 1 / over 2 / burst 2 / xtreme 3）让高风险的攻击型与稳健的耐力型有不同的期望值，比赛有悬念。

### 3.2 信息架构（页面树）【设计】

```
启动 / 加载
└─ 主界面（Home）
   ├─ 继续：上次进行中的挑战 / 锦标赛（有存档时）
   ├─ 对战（Play）
   │   ├─ 快速对战（自由对战）
   │   ├─ 挑战之路
   │   ├─ 试转台（练习 / 教学 / 属性实测）
   │   ├─ 锦标赛（V1.1）
   │   ├─ 连战（V1.1）
   │   └─ 双人同屏（V1.1）
   ├─ 车库（Garage）
   │   ├─ 我的构筑（保存的组合，最多 12 个）
   │   ├─ 组装（现有 GarageScreen 扩展）
   │   └─ 零件图鉴（已拥有 / 未拥有 / 获取方式）
   ├─ 竞技场图鉴（地图说明、规则影响）
   └─ 设置
```

对局内流程（所有模式共用一条"比赛管线"）：

```
模式规则 → 对手 / 场地确定 → 战斗准备页 ──→ 发射（回合 n）→ 战斗 HUD → 回合结算条
                ↑                                                    │
                └──────── 赛间调整页（换零件 / 战术）←── 未分胜负 ───┘
                                                                     │ 有人到 4 分
                                                                     ↓
                                                               比赛结算页 → 重赛 / 下一关 / 返回
```

### 3.3 与现有阶段机的关系

【事实】`GameEngine.ts:25` 现在的阶段为 `'loading' | 'title' | 'garage' | 'aim' | 'battle' | 'paused' | 'result' | 'error'`，页面和战斗共用一个状态机，结果写存档在 `onResult`（`GameEngine.ts:891-907`）。

【设计】拆成两层：
- **App 路由层**（React，新）：Home / Play / Garage / Settings / MatchFlow 等页面，持有"当前比赛"对象。
- **比赛层 `MatchSystem`**（纯 TS，新，可无头测试）：回合、计分、换边、赛间调整合法性、结束条件；内部每回合创建一个 `BattleSystem`。
- **战斗引擎层**（现有 `GameEngine` 收缩）：只负责场景、发射、战斗渲染与回合结果回调。

这样可以在 Node 里无头跑完整场比赛（复用 `tests/sim.ts` 思路），给赛制和平衡做统计。

## 4. 核心战斗体验设计

| 阶段 | 玩家看到 / 做什么 | 系统定义 | 依赖 |
|---|---|---|---|
| 准备 | 对手构筑与类型（情报等级随模式）、场地规则卡、自己的构筑与实测属性；可选"战术指令" | 组装合法性检查、实测属性读取、对手构筑与发射风格（难度）、场地规则 | MatchSystem、实测属性表 |
| 发射 | 3-2-1 倒计时；拉绳：拉长 + 松手速度 = 力度，左右 = 方向，把手倾斜 = 倾角；可在本方发射区内左右挪动发射位 | `LaunchCommand {power, aim, tilt, slot}` → `computeLaunch` 的初始位置 / 速度 / 转速 / 倾角；对手按难度生成指令 | 开放 `tilt`（`PullStringGesture.ts:90`） |
| 开局交锋 | 双方落地，各自按性格找位置 | Tactical AI `launch → roam/orbit/cut`；驱动按轴心物理能力执行 | 阶段 2 驱动模型 |
| 中段战斗 | 追击、环绕、切入、碰撞、反弹、再接近；HUD 只显示转速与事件 | 接触事实（ContactService）→ 接触分类 → 反馈与爆裂累积；AI 读真实观测调整 | 阶段 1–3 |
| 终结 | 爆裂 / 出界 / 极限 / 旋转终结；终结后 2–3 秒慢动作回放（可跳过） | 终结判定优先级（4.6）；回放用记录的变换数据，不重跑物理 | 传感器口袋、爆裂模型、回放缓冲 |
| 结算 | 回合结算条（谁得几分、怎么赢的）；比赛结束后统计、奖励 | 回合统计、比赛统计、奖励规则 | MatchSystem、SaveStore v2 |

### 4.2 玩家影响发生在哪里

| 时机 | 决策 | 是否影响物理 |
|---|---|---|
| 赛前 | 构筑（3 个零件）、战术指令、发射风格偏好 | 零件 = 物理参数；战术指令 = 己方 Tactical AI 的性格参数（只改"想去哪"，执行仍受驱动物理约束） |
| 发射时 | 力度、方向、倾角、发射位 | 决定初始状态 |
| 回合间 | 换 1 个零件 或 换战术指令；锦标赛中换整台陀螺 | 同赛前 |
| 比赛中 | **只有**镜头切换、暂停 | 不影响 |

【设计决策】比赛中**不加入**任何"应援 / 气势 / 技能按钮"。理由：任何比赛中输入要么是对物理的伪造（违反任务书 1.2 与裁决 3.1），要么是无效按钮（损害信任）。

**战术指令**【设计】：3 个选项，作用于己方 `MotionProfile`（【事实】`motionIntent.ts:122-125` 现在 `aggression` 由 Blade 的 attack/defense 推出）：
- 主动：提高切入倾向、缩短环绕时间；
- 稳守：倾向守中、闪避阈值降低；
- 自动：按零件推断（现状）。

指令不能让针尖获得它物理上没有的驱动力——这正是"受物理约束"的含义，也让零件选择保持意义。

### 4.3 AI 战术状态（在现有状态机上重定义）

【事实】`motionIntent.ts:18` 已有 `launch / roam / orbit / cut / contact / disengage / guard / evade / breakout`。

【设计】保留前 8 个，删除 `breakout`（它是脱困补丁的入口）。状态切换输入必须来自统一观测层：

| 输入 | 来源 | 用途 |
|---|---|---|
| 外沿距离、相对速度、接近角 | 刚体状态 | cut / orbit / evade 切换 |
| 接触状态（无 / 轻擦 / 持续 / 重击） | ContactService + 分类 | contact / disengage |
| 自身与对手剩余转速比 | 刚体角速度 | 低转速时攻击型转保守、耐力型转守中 |
| 场地位置（中心区 / 坡面 / 轨道 / 口袋附近） | ArenaSpec 区域查询（取代 `edgeR 3.4` 常数） | 墙边保护、轨道利用 |
| 控制效果反馈 | 期望方向 vs 实际加速度 | 判断"推不动"→ 换策略，而不是加力 |

### 4.4 接触分类（玩家可感知的 5 种）

| 类别 | 判定（基于 ContactService 事实） | 反馈 |
|---|---|---|
| 轻擦 | 接触时长 < 0.05 s，法向冲量小 | 小火花、轻音 |
| 侧撞 | 切向相对速度 ≫ 法向接近速度 | 沿切向的火花带、刮擦音 |
| 正面重击 | 法向接近速度高、冲量大（现有 heavy tier） | 闪光、冲击波、震屏、重音（中低画质保留闪光） |
| 持续接触 | 同一接触段 > 0.3 s（现有 `contactFeedback.ts` 接触段） | 持续摩擦火花、嗡鸣 |
| 墙 / 轨道碰撞 | 陀螺对场地碰撞体 | 轻量火花，不震屏 |

【事实】现有三档（`impactTiers.ts`）+ 接触段（`contactFeedback.ts`）已覆盖前 4 类的一大半；需要补"侧撞 vs 正面"的方向区分和墙碰撞类。

### 4.5 低速与僵持：不用强制分离的处理方式

分三层，**只有第一层是解决问题，后两层是规则兜底**：

1. **根治（阶段 2）**：驱动模型重建，让每种轴心在低速时有与其几何相符的运动能力（球头会滚、针尖会在倾斜时走），并删除 `driveMinGrip` 式一刀切门槛（裁决 3.1 硬性约束）。
2. **物理自然结局**：转速下降 → 自稳减弱 → 倾斜增大 → 刮地衰减（`BEY_TUNING.scrapeDecay`）→ 旋转终结。这本来就是陀螺比赛的结局方式。
3. **规则兜底【设计】**：回合上限 60 秒（可按模式配置），到时按剩余转速比判"旋转判定"得 1 分，转速比差 < 5% 判平局重赛。这是裁判规则，不改变任何物理状态。**验收要求**：标准对手池中超时回合占比 < 5%；一旦超过，说明根治没完成，不许靠调兜底规则掩盖。

### 4.6 终结规则与优先级【设计】

| 终结 | 得分 | 判定（事实来源） | 现状 |
|---|---|---|---|
| 极限终结 | 3 | 陀螺质心进入**极限口袋传感器体积**并停留 ≥ 0.1 s | 按角度判定（`BattleSystem.ts:410-416`），需重做 |
| 出界终结 | 2 | 进入出界口袋传感器，或越过外墙落到台面 | 半径 / 高度判定，需改为传感器 |
| 爆裂终结 | 2 | 锁盘锁止累计值达到阈值（6.4 节），Blade 与 Disc 分离 | 不存在 |
| 旋转终结 | 1 | 转速 < 阈值或倾倒刮地持续 0.5 s（现有 `BattleSystem.ts:417-419`） | 保留 |
| 旋转判定 | 1 | 回合超时，比较转速比 | 现在 120 s 后比较转速（`BattleSystem.ts:441`），改为 60 s 可配 |

同一判定帧双方都终结：得分高的终结类型优先归属（例如 A 被极限终结、B 同时旋转终结 → B 得 3 分）；同类则判平局重赛（现在是比较剩余转速，`BattleSystem.ts:430-433`，在回合制下平局重赛更公平且更有戏剧性）。

### 4.7 镜头、特效、音效、UI 的强调规则

- 实时比赛中：**不慢动作、不定格**（尊重 P2.2.1 用户决定）；重击用闪光 + 冲击波 + 短震屏 + 音效；HUD 事件提示只出现在屏幕上缘中部小字，0.8 秒淡出，不遮挡场地中心。
- 终结时：主镜头不跳切，先保持 0.5 秒让玩家看清；然后弹出"终结回放"——用最近 3 秒的刚体变换环形缓冲（2 台 × 60 fps × 3 s，约 360 条记录，内存可忽略）以 0.35 倍速重播最后 1.2 秒，可点击跳过。回放不重跑物理，因此不受跨设备浮点差异影响。
- 振动：接入 `@capacitor/haptics`，重击 / 终结各一档（【事实】iOS 无 `navigator.vibrate`）。
- 性能：所有强调效果走现有画质分档；撞击闪光在所有档保留（用户决定）。

## 5. 四类陀螺定位、克制关系与首发代表组合

### 5.1 四类是否够用

【判断】四类作为**主定位**够用，而且是玩家已经熟悉的语言；但只有主定位不够表达构筑差异，增加两个**次要维度**：
- **旋转方向**（右旋 / 左旋）：左旋与右旋相撞时接触面相对速度不同（正面相对而非顺向摩擦），这是真实物理差异，不需要新规则。V1.1 引入，先做 1 个左旋 Blade。【事实】现在全部右旋（`catalog.ts` 每个 Blade `spin: 'right'`），`BeyPhysics.ts:185` 已支持左旋符号，但从未测试。
- **战术标签**（由实测数据自动打上，不手写）：例如"突进"（平均速度高）、"压中"（中心区停留比高）、"反击"（被撞后速度反超率高）、"持久"（单人试转时长长）。标签是展示，不是数值加成。

### 5.2 四类定位表【设计】

| | 攻击型 | 防守型 | 平衡型 | 耐力型 |
|---|---|---|---|---|
| 主要赢法 | 极限 / 出界终结（2–3 分） | 让对方撞上后自己飞出、或熬到对方旋转终结 | 前半场攻、后半场稳，按对手调整 | 旋转终结 / 旋转判定（1 分） |
| 物理机制（不是数值） | 少刃、大凸起 Blade → 接触点少而深，冲量集中；高摩擦宽平轴心 → 强驱动、能用轨道；轻 Disc | 多段圆弧 Blade → 接触点多而浅、冲量被分散、对方更容易被反弹；重；宽球头轴心 → 抗倾倒 | **变轨轴心**：高转速时接触面宽（有驱动），转速降到阈值后接触面收窄（低摩擦）；刃形攻守混合 | 外缘配重 Blade（真实惯量大）；低摩擦尖轴心；低空气阻力轮廓 |
| 典型行为 | 花瓣轨迹大范围移动，切入、撞后反冲 | 守中心区、移动少、被撞后回中 | 开局主动、中段之后收缩到中心 | 几乎不移动、尽量避免接触 |
| 优势 | 唯一能稳定拿 3 分的类型 | 对攻击型：对方高速撞来，反冲常把对方送出界 | 对任何类型都不会大幅劣势 | 对防守型：防守型移动耗转，熬不过 |
| 代价（必须真实存在） | 驱动与撞击消耗转速；冲太快会自己进口袋（自毁）；对耐力型撞不到就输转速 | 重 → 转速上限低（`assemble.ts:61` `maxSpin` 随质量降低）；对耐力型拿不到高分 | 什么都不极端；切换时机取决于发射力度 | 被重击容易出界、易爆裂（轻 Disc 时） |
| 克制 | 克耐力（撞得到就赢） | 克攻击（反冲） | 无硬克制 | 克防守（转速经济） |
| 反制方式 | 防守对手 → 换高锁盘提高打击高度 / 降低发射力度减少自毁 | 耐力对手 → 换高摩擦轴心主动出击 | 看对手换轴心 | 攻击对手 → 换重 Disc、宽轴心，牺牲一点耐力换抗冲击 |
| 外观语言 | 方向性突起、锐利分层、红 / 橙点缀 | 连续厚甲、圆润、低突出、蓝点缀 | 攻守结构混合、银 + 蓝（沿用用户已定"疾风新月"配色） | 流线外缘、配重金属环、紫点缀 |

**颜色说明**：概念图把类型色铺满整台陀螺；但用户 P2.3 已定平衡型"疾风新月"为银 + 蓝，与防守型蓝色冲突。建议**类型色只用于 UI 徽标、属性条和透明件点缀**，陀螺本体配色跟随各自的参考图。这样既不推翻用户已有决定，又能保持类型识别。

### 5.3 克制目标与验收【设计】

目标胜率矩阵（行对列，首发 4 个代表组合，标准场，100 回合多种子，双方随机发射参数在合理区间）：

| | 攻 | 守 | 衡 | 耐 |
|---|---|---|---|---|
| 攻 | 50 | 35–45 | 45–55 | 55–65 |
| 守 | 55–65 | 50 | 45–55 | 35–45 |
| 衡 | 45–55 | 45–55 | 50 | 45–55 |
| 耐 | 35–45 | 55–65 | 45–55 | 50 |

额外指标：
- 终结类型分布：攻击型获胜回合中出界 + 极限 ≥ 60%；耐力型获胜回合中旋转终结 + 判定 ≥ 70%。这是"赢法不同"的可测证据。
- 行为可观察：四个代表组合在单人试转中的平均水平速度、中心区停留比、接触次数，彼此差异至少 30%。
- 硬克制禁止：任何一格 > 70% 视为失败。
- 双方换边后胜率差 < 5 个百分点（检验场地对称性）。

【事实】现成工具：`tests/diag/types.diag.ts` 三型循环赛，可扩展为这张矩阵的自动测量。【报告】现状不达标：攻击型对防守 / 耐力基本赢不了。

用任务书的 2 字名作为**组合名**（玩家记忆点），零件沿用仓库已有的原创零件名，保持连续性：

| 组合名 | 类型 | Blade | Disc | Tip | 设计要点 |

## 6. 模块化零件与属性体系

### 6.1 三零件职责【设计】

| 零件 | 中文 | 决定什么（物理） | 新增 / 修改字段 |
|---|---|---|---|
| Blade | 刃环 | 接触几何（刃数、凸起深度、刃面角度）、主要质量、外缘惯量、旋转方向 | 新增 `contact: { lobes, protrusion, rakeAngle, smooth }` 生成**复合凸包碰撞体**，取代圆柱；`attack/defense` 标量逐步退役（由几何产生） |
| Disc | 锁盘 | 高度（决定刃环打击高度）、锁齿数（爆裂所需累计）、靠近中心的质量（稳定性） | 新增 `teeth`、`lockStrength`；`burstResistance` 由两者计算；高度已存在 |
| Tip | 轴心 | 接地几何（球 / 平 / 尖 / 宽）、摩擦、轨道咬合、低速稳定性、驱动能力 | 新增 `contactShape`（含平底宽度、可选 `transition` 变轨参数）；`gearGrip` 改为轨道材质交互参数；`drift` 由几何推导 |

**为什么 Disc 用"打击高度"而不是只当配重**：【事实】`assemble.ts:46-48` 层高按 Tip → Disc → Blade 堆叠，Disc 越高刃环越高；Disc 碰撞半径 0.30–0.34 远小于 Blade（审查 B-5），所以 Disc 本身几乎不参与碰撞。高度差让高刃打低刃的上缘、低刃从下方顶起对方——这是真实陀螺的高度博弈，物理上由碰撞体位置自然产生，不需要新规则。

### 6.2 兼容规则【设计】

- 首发：任意 Blade × Disc × Tip 全部兼容（降低学习成本，真实玩具也基本如此）。
- 合法性检查只做：3 个槽位都有零件、零件已拥有、锦标赛"三台不得重复同一零件"。
- 保留扩展口：`PartBase` 加可选 `requires` / `excludes`，留给将来的一体式特殊零件。

### 6.4 爆裂模型【设计，依赖阶段 1–4】

- 真实机制：撞击给刃环一个相对锁盘"反向转"的冲击，锁齿每被顶过一格就松一点，累计到底就分离。
- 游戏模型：每次 Blade 对 Blade 接触，按 ContactService 的法向冲量 × 接触面相对切向速度方向，估计"逆旋转冲量"；超过锁齿阈值记 1 格；格数达到 `teeth` 时爆裂；格数随时间不回复（同一回合内累计）。
- 表现：Blade 与 Disc 分离成两个刚体飞出（爆裂后才生成新刚体，不影响爆裂前物理）。
- 【未知 / 风险】ContactService 报告指出 Rapier 的切向冲量不可用（Simplified 摩擦不写回，实测全 0）。所以逆旋转冲量只能由"法向冲量 + 接触点表面相对速度"推导，属于**推导量**，必须在观测层标为推导而非物理事实（裁决 4）。验收：爆裂率随锁齿数单调下降、随攻击型刃凸起深度上升；标准对局中爆裂占终结 10–25%。
- 为什么值得做：没有爆裂时 Disc 只剩高度和配重，攻击型对防守型也缺少"打得赢的路"。

### 6.5 实测属性管线【设计】

| 展示属性 | 定义（标准测试） | 测量方式 |
|---|---|---|
| 冲击 | 对标准假人陀螺正面切入 20 次，假人平均获得的水平速度变化 | 无头模拟，固定种子 |
| 防护 | 被标准攻击陀螺撞 20 次，自身平均速度变化的倒数（归一） | 同上 |
| 耐力 | 标准力度单人试转，从发射到旋转终结的时长 | 同上 |
| 机动 | 单人试转前 8 秒平均水平速度与覆盖面积 | 同上 |
| 稳定 | 被撞后倾角恢复到 0.1 rad 内所需时间 | 同上 |
| 抗爆 | 标准攻击陀螺使其爆裂所需撞击次数中位数 | 爆裂模型上线后 |
| 重量 | 零件质量之和 | 数据 |

做法：`tools/bench/` 下一个脚本复用 `stage1/reproducible-baseline` 的确定性记录器，对所有组合跑基准，输出 `measuredStats.json` 随包发布；`benchVersion` 绑定物理参数快照（现有 `tests/fixtures/physics-snapshot.json`），物理一改 CI 就提示重算。UI 中组装页的属性条和"换件前后差值"都读这张表。

**好处**：属性条有清晰来源（任务书第 8 节要求）；平衡调参时直接看这张表，不用玩很多局；玩家看到的排序与实战一致。

### 7.1 首发主场「标准竞技场」现状【事实，按 `arenaSpec.ts` 公式计算】

单位为游戏单位（1 单位 ≈ 刃环半径的 2 倍；Blade 半径 0.49–0.53）。场地半径 5.4 / 刃环外径约 1.0 → 直径比约 10.8，与真实"约 45 cm 场地 / 约 4.5 cm 陀螺"同一量级【推断】。概念图里的"Ø120 mm 场地 / Ø60 mm 陀螺"比例明显错误，不采用。

剖面（`floorHeight(r)`，坡角为切线角）：

| 半径 r | 0 | 0.6 | 1.5 | 2.5 | 3.17（发射半径） | 3.6 | 4.2 | 4.75 | 5.0 | 5.4（墙） |
|---|---|---|---|---|---|---|---|---|---|---|
| 高度 | 0 | 0.001 | 0.094 | 0.290 | ≈0.48 | 0.619 | 0.861 | 1.181 | 1.373 | 1.763 |
| 坡角 | 0° | 1.8° | 8.4° | 13.8° | ≈17° | 19.4° | 25.5° | 35.1° | 40.1° | 48.0° |

墙高 1.1（墙顶约 2.86），3 个口袋：极限 −90°（宽 2.6、深 1.7）、出界 30° 与 150°（宽 1.85）。"极限轨道"是 r 4.75–5.4 的脚本冲刺带，正好落在 35°–48° 的陡坡上。

### 7.2 首发主场重设计【设计】

保留碗形剖面（它已经过多轮调参，【报告】碗面变浅会让中段交锋减半），只改 4 件事：

1. **发射对称**：发射区从"玩家 90° / 对手 −90°"改为左右两侧 180° / 0°（相对极限口袋所在轴镜像对称），每回合换边。理由：现在对手正对极限口袋、玩家半场有两个出界口袋。由于两台都是右旋，镜像位置在手性上仍不完全等价，所以必须配合"每回合换边"，并用换边胜率差 < 5 个百分点验收。
2. **轨道变成真实区域**：在 r ≈ 4.4–5.0 加一圈**坡度放缓的环形台阶**（视觉为齿轮纹轨道，碰撞上是一条坡角约 15° 的独立环形碰撞体，带自己的摩擦材质）。齿轮 / 橡胶轴心在这条材质上得到更高的牵引，是驱动模型里"接地材质 × 轴心几何"的结果，而不是脚本冲量。轨道入口在极限口袋前方收窄成"冲刺线"——高速沿轨道跑的陀螺有可能直接冲进极限口袋，这正是攻击型的高风险高收益。
3. **口袋用传感器判定**：每个口袋一个 Rapier 传感器碰撞体（只产生进入事件，不施加力），终结判定读传感器事实。
4. **区域数据化**：中心区、碗面、轨道、口袋、墙全部写在 `ArenaSpec.zones` 里，AI 墙边阈值、镜头范围、发射区都从这里读（替代 `motionIntent` 里写死的 `edgeR 3.4`）。

## 8. 游戏模式与规则表

### 8.1 标准比赛规则（所有模式默认）【设计】

- 先到 4 分获胜；终结得分见 4.6；平局回合重赛不计分。
- 每回合后双方换边。
- 回合间可换 1 个零件或战术指令（快速对战可关闭）。
- 回合上限 60 秒，超时旋转判定 1 分。
- 发射：3-2-1 倒计时后双方同时发射；玩家拉绳不限时，对手在玩家松手时同时发射（现有行为，`GameEngine.ts:214-216`）。

### 8.2 模式总表

| 模式 | 目标 | 单局流程 | 胜负 | 奖励 / 解锁 | 复玩动机 | 版本 |
|---|---|---|---|---|---|---|
| 快速对战 | 随时来一场 | 选构筑 → 选对手（任意已解锁）→ 选场地 → 标准比赛 | 标准规则；可设"单回合" | 只记战绩 | 试构筑、练发射 | MVP |
| 挑战之路 | 推进与学习 | 12 关线性 + 3 个 Boss；每关固定对手构筑与 1 条关卡目标 | 赢下比赛；关卡目标（如"用极限终结得分"）给额外星 | 每关解锁 1 个零件 / 对手 / 场地；3 星给外观 | 星数、解锁全零件 | MVP |
| 试转台 | 教学与理解 | 无对手单人发射；显示实时转速曲线、轨迹；可放"标准假人" | 无 | 首次完成教学解锁快速对战 | 看懂零件 | MVP |
| 锦标赛 | 高潮内容 | 8 人单败；赛前提交 3 台陀螺（零件不得重复），每回合从中选 1 台出战 | 每场先到 4 分 | 冠军解锁稀有零件 / 称号 | 赛制深度、卡组构筑 | V1.1 |
| 连战 | 耐力挑战 | 连续对 N 个随机构筑，不能换零件，每场单回合 | 输一场结束 | 记录最高连胜 | 排行（本地） | V1.1 |
| 双人同屏 | 线下社交 | 两位玩家轮流组装，左右各一个拉绳区同时发射 | 标准规则 | 无 | 和朋友玩 | V1.1 |
| 每日挑战 | 轻量更新感 | 按日期种子离线生成"对手构筑 + 场地 + 1 条规则修饰"，无需联网 | 标准规则 | 外观 / 称号 | 每天不同 | V1.2 |
| 在线对战 | — | 需要服务器权威、确定性跨设备一致性、反作弊 | — | — | — | 不承诺，单独立项 |

**为什么挑战之路比"剧情模式"优先**：剧情需要角色、文案、过场——成本高且容易碰 IP；挑战之路用"对手构筑 + 关卡目标"就能承担教学（第 1–4 关各教一种类型的打法），全部数据驱动。

**为什么双人同屏成本低**【推断】：比赛中无操作，双人只需要两套发射输入；横屏左右各一个拉绳区在 844 pt 宽度下可行；不需要网络同步。主要工作是第二套拉绳 UI 和两边组装流程。

### 8.3 AI 难度（只改"决策"，不改物理）

| 难度 | 对手构筑 | 发射质量 | 赛间调整 |
|---|---|---|---|
| 新手 | 固定、偏弱组合 | 力度 0.5–0.75，方向随机 | 不调整 |
| 标准 | 关卡设定 | 力度 0.65–0.9（现有 0.55–0.95） | 输一回合后 50% 概率换 1 零件 |
| 高手 | 针对玩家类型选克制构筑 | 力度 0.8–0.95，倾角利用 | 每回合按上一回合终结方式换件 |

禁止：任何难度给对手增加转速、质量、摩擦或驱动加成。

## 10. 成长、收集与复玩

- **获取方式（无付费、无抽取）**：挑战之路每关固定奖励 1 件；挑战星数里程碑给外观（配色方案）；锦标赛冠军给稀有零件；每日挑战给外观。首发全部零件可通过挑战之路拿到，不设概率。

## 11. 知识产权与原创边界

【事实】仓库里与品牌相关的文本：
- `ui/App.tsx` `SpinBar` 显示 "XTREME DASH"；
- `BattleSystem.ts:15` 终结类型 `xtreme` 与"极限终结"标签；
- README "受 Beyblade X 结构启发的原创…"；产品名 "BBX"。

【事实】任务书概念图中出现 "Xtreme Dash"、"Ratchet / Bit"、"3-60 / 4-80 / 5-70 / 6-60" 式编号、"BBX" Logo。

【推断，非法律意见】风险从高到低：
1. **商品名 / 标识**："BBX"作为游戏名与 Beyblade X 的常见缩写高度相似；"Xtreme Dash"是对方产品宣传用的机制名。建议换原创产品名（例如"旋锋竞技场 / SPIN FORGE"之类，需用户选定），HUD 改用"轨道冲刺 / RAIL RUSH"。
2. **零件命名体系**："刃数-高度"的数字编号法（3-60）是对方独特的命名表达。本方案不采用，零件用原创中文名 + 原创英文代号（现有 `code` 字段，如 BLAZE FANG）。
3. **规则机制**：积分终结（1 / 2 / 3 分）、三段式结构、口袋场地属于通用玩法机制，一般可借鉴；但措辞（"极限终结"等）建议在发布前统一换成原创名称。
4. **外观**：所有模型按各自参考图原创制作，中心徽标原创（用户视觉标准）；不复刻任何具体官方陀螺造型。

如果项目只自用不发布，以上风险都很低；一旦上架或公开分发，第 1 项是必须先处理的。这是第 14.3 节决策 1。

## 12. 分阶段落地路线

### 12.1 双轨原则

- **A 轨（物理与战斗，遵循 ChatGPT 裁决阶段 1–4）**：每阶段需要单独授权、有量化验收与回滚边界。
- **B 轨（产品外壳与内容，不依赖驱动模型）**：页面、赛制、存档、内容数据层、画质低档、IP 文本。B 轨的每项都在现有物理上就能玩，并且在 A 轨改进后自动受益。
- **汇合点**：里程碑 M3"四型可辨"需要 A 轨阶段 2–3 完成。

为什么不按顺序做：如果 B 轨等 A 轨，产品会继续停在"单局实验"状态（这正是用户 2026-11-08 对过往工作的批评）；而 B 轨的工作和物理代码几乎不交叉（主要改 `ui/`、`core/`、`storage/`、新增 `match/`、`content/`），可以并行而不污染物理对照实验。
