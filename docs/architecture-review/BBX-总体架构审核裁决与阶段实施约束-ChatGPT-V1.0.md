## 1. 总体审核结论

原则上批准以 Stage A `2f573ab` 作为正式重构基线，并仅移植 `e72164c` 中经逐项审查确认的画质分档及独立渲染优化。

不批准将以下内容带入正式代码线：

- 通用程序性僵持脱困机制；
- V1 `stallRoll` 滚阻补丁；
- 与画质无关的临时测试 IPA、runner 或一次性配置。

补丁无冲突地应用，不代表语义安全。必须逐文件、逐代码块审查，确认不改变物理行为、AI 决策、战斗结果或游戏规则。

本次审核只形成架构裁决，不授权代码修改、分支操作、提交、PR、合并、构建或发布。

## 2. 正式基线与阶段性问题

### 2.1 基线定义

- **B0：** Stage A `2f573ab`。
- **B1：** B0 加上 `e72164c` 中经确认的画质分档和相关渲染优化。
- 不把 `e72164c` 整体作为正式基线。

### 2.2 球头对球头僵持

正式代码线接受阶段 2 完成之前，球头对球头可能出现原地僵持。这是明确接受的阶段性问题，不是最终产品可接受的体验。

阶段 2 必须将其列为核心验收目标。不得为了当前试玩观感重新启用通用程序性拉开机制，以免污染运动模型和对照实验。

特殊试玩构建若未来确有需要，应与正式代码线隔离，明确标注实验性脱困，不得用于评价正式运动模型。

## 3. 运动控制总体架构

采用以下闭环：

**Tactical AI → Motion Controller → Physics Simulation → Unified Physics Observation / Battle Rules → Feedback to AI**

职责边界：

1. Tactical AI 负责战术意图，例如追击、切入、环绕、调整策略和脱离。
2. Motion Controller 将战术意图转换为受物理能力约束的控制请求。
3. 轴心驱动模型依据真实轴心几何、摩擦、接触、倾角、自转和执行能力产生实际物理作用。
4. Rapier 负责物理模拟，不由 AI 直接伪造物理状态。
5. 统一观测层反馈真实运动、接触、姿态、自转损耗和控制效果，供 AI 调整策略。

### 3.1 控制接口与执行算法的区分

统一控制接口方向：

- 期望方向；
- 控制强度；
- 目标/行为上下文；
- 有效期限或更新周期；
- 必要的控制约束与状态反馈。

方向 + 强度是接口设计方向，但不预先裁定底层执行算法。

保留两种候选实现进行公平对照：

- A：方向 + 强度执行方式；
- B：相位偏置执行方式。

在相同初始状态、随机种子、陀螺/部件、场地、对手和统计口径下比较。根据实际运动结果、物理约束、能量消耗和战斗体验决定，不凭理论偏好提前定胜负。

硬性约束：

- 不使用瞬移、无约束速度注入、强制朝向等伪造自然追击；
- 不因某轴心的驱动能力低于单一门槛就完全关闭其控制执行；
- 不能把“加速度方向发生变化”当作“自然追击能力成立”。

## 4. 统一物理观测与接触服务

ContactService 的建立分两步：

### 第一步：只读观测

统一采集接触事实，包括可获得的接触点、法线、相对速度、冲量等。明确区分：

- Rapier 暴露的真实物理事实；
- 游戏层根据事实推导的状态；
- 预测值或启发式估计。

只读阶段不得改变碰撞、AI、死亡摇摆或胜负规则。

### 第二步：消费者逐个迁移

逐个迁移碰撞、AI、死亡摇摆和战斗规则消费者。每个迁移都要检查：

- 迁移前后行为差异；
- 碰撞判定是否变化；
- 战斗结果是否变化；
- 时序是否变化；
- 是否有独立回滚路径。

统一观测不等于统一改变所有消费者行为。

## 5. 惯量与物理状态所有权

惯量统一不能仅比较游戏层 `spinInertia` 与 Rapier 某个标量。

先核实：

- 质量与质心；
- 刚体和局部坐标系；
- 完整惯量张量与主惯量轴；
- 轴心、Blade、Disc 等组合部件的质量分布；
- Rapier 实际读取的质量属性；
- 游戏层与物理层的坐标和单位转换。

非对称结构必须考虑完整惯量张量，而不只是自转轴上的标量。

同时明确物理状态所有权：哪些状态由 Rapier 积分，哪些由游戏逻辑控制，哪些只是观测量。特别调查 `setAngvel()` 等直接写状态操作与约束求解之间的相互作用，不允许未经测量就归因。

## 6. 能量与角动量账本

建立可解释的能量账本，至少区分：

- 平动动能；
- 转动动能；
- 重力势能；
- 碰撞前后能量变化；
- 摩擦和物理约束造成的变化；
- 游戏代码直接修改角速度产生的变化；
- 数值误差和未解释残差。

同步记录角动量相关数据。角速度变化不能直接等同于能量损失；应结合质量、惯量、线速度和角速度计算。

重点调查 `setAngvel()` 与 Rapier 约束求解的交互。未得到证据前，不得宣称某机制已被证实为能量异常根因。

## 7. 阶段 2 自主运动验收

除低速僵持外，至少覆盖：

- 追击成功率；
- 有效切入率；
- 自然碰撞分离率；
- 分离后的重新接近率；
- 运动方向变化连续性；
- 无效控制指令占比；
- 不同轴心的有效控制范围；
- 自转消耗与运动收益关系；
- 不同发射方向、初始自转、倾角和场地位置。

测试应覆盖多种轴心/Blade 组合、初始条件和对手行为。不能只用少数固定场景证明系统有效。

## 8. 帧率与真机性能裁决

目前不裁定 GPU 受限，也不裁定约 48 FPS 必然是 ProMotion 48 Hz 档位。两种因素可能同时存在。

阶段 5 应交叉测量：

- 原生显示刷新节奏（例如 CADisplayLink）；
- WebView `requestAnimationFrame` 回调节奏；
- CPU 主线程耗时；
- GPU 工作时间；
- 帧间隔分布；
- 长时间运行后的温度、降频或刷新档位变化。

不能仅凭 rAF 约 48 Hz 判定 GPU 瓶颈，也不能仅凭稳定 48 Hz 间隔排除 GPU 瓶颈。

性能验收应基于设备实际可用刷新档位，考核节奏稳定性、漏帧、性能余量和画质档位收益，不得把所有设备稳定 60 FPS 设为无条件硬指标。

## 9. 六阶段总体实施顺序

0. **正式工程基线与治理：** 明确 B0/B1、分支与 PR 状态、历史成果去留、工作区和构建配置。
1. **统一物理基础设施：** 固定随机种子、建立可信测试基线、只读 ContactService、惯量契约、物理状态所有权、能量/角动量账本。
2. **自主运动与 AI 控制重建：** 统一控制接口、反馈闭环、不同轴心驱动、对照实验和自然战斗验收。
3. **碰撞与攻防升级：** 保留 Rapier 核心，针对重击、持续接触、攻防差异和接触响应做证据驱动改进。
4. **竞技机制完善：** 让自转、出界、位置优势、压制、反击及未来爆裂等共同构成胜负机制；避免自转成为唯一胜负条件。
5. **工程架构与性能：** 按真实职责逐步拆分模块，进行 CPU/GPU/刷新率真机验证；避免无收益的大规模重写。
6. **完整体验与交付：** 完成完整对战循环、模式、组装、竞技场、AI 风格、回放/镜头、音效、设置、稳定性和 IPA 真机验收。

阶段之间必须有明确交付物、量化验收、回滚边界和进入下一阶段的授权。不能因阶段计划存在就自动获得后续实施权限。

## 10. 通用验收原则

每阶段验收都必须覆盖：

1. 产品体验收益；
2. 架构职责和依赖是否清晰；
3. 机制根因是否得到证据支持；
4. 数据与实验是否可复现；
5. 回归测试和对照结果；
6. 性能与资源成本；
7. 真机体验（适用时）；
8. 回滚能力与后续风险。

拒绝只用代码行数、测试通过率、单一场景改善或报告长度证明成功。

测试应区分确定性回归与多种子统计测试。固定种子保证可复现，多种子样本用于评估行为分布；不得用增加重试次数掩盖随机性。
